# Domain KG Implementation Plan

> **For agentic workers:** Implement this plan task by task using native execution and the project `AGENTS.md`. Superpowers `executing-plans` is a compatible optional workflow. Steps use checkbox syntax for tracking. This planning handoff does not start implementation or delegate work.

**Goal:** Build a shared, permission-aware web MCP server that manages multiple KGs and databases, preserves work materials, maintains evidence-backed graphs, and combines graph, vector, and lexical retrieval.

**Architecture:** A FastAPI/MCP service uses LightRAG for construction and scoped retrieval. MongoDB owns the catalog, permissions, material/evidence revisions, jobs, and publication manifests; Neo4j and Qdrant serve source-aware projections, and S3 preserves originals. Graph/vector readiness precedes MongoDB acceptance, with durable repair instead of a distributed transaction.

**Tech Stack:** Python 3.12, FastAPI, official MCP Python SDK, LightRAG, MongoDB replica set with PyMongo async API, Neo4j, Qdrant, Pydantic, Docling, S3 compatible storage, external OIDC, Jinja2/HTMX, pytest, Ruff, and mypy.

**Spec:** [System design](../../design.md), [contracts](../../contracts.md), [publication protocol](../../revisions-and-publication.md), and [acceptance](../../acceptance.md).

## Global constraints

- Implement a shared team service. Identity, permissions, and management of multiple KGs belong to the initial release.
- Namespace every material, graph object, vector, job, cache entry, and citation by organization and KG.
- The persistence stack is LightRAG, MongoDB, Neo4j, Qdrant, and object storage, with no relational database or SQL layer.
- Each KG uses one registered storage profile with explicit namespaces. Search across profiles does not claim a distributed snapshot.
- MongoDB owns accepted views. Stage and verify immutable graph/vector revisions before publication; do not claim cross-store atomic writes.
- Verify access before retrieval and again before returning results. Every evidence-derived field must obey source visibility.
- Originals and immutable parsed source blocks are preserved. Assertions require supporting spans, explicit manual curation provenance, or imported-unverified provenance.
- Default retrieval uses accepted active versions and verified source or explicitly manual curation supports; imported-unverified relations are excluded.
- Fast mode uses filtered vector/text recall without generative query LLMs, graph expansion, or reranking. Deep mode adds scoped graph exploration.
- Manual node/relation edits survive source re-ingestion and rebuilds; rollback appends a new revision under current permissions.
- Query length is 1–8,000 characters; KG selection is 1–10; top-k is 1–50.
- Graph traversal is 0–2 hops, at most 200 nodes and 400 edges per KG, with limits enforced during expansion.
- Default chunk target is 700 tokens with at most 100 tokens overlap. Default final evidence text budget is 24,000 characters.
- Upload limit is 50 MiB; PDF job limit is 500 pages; unclaimed uploads expire after 24 hours.
- Provider requests and imported content cannot change permissions or execute database commands.
- Backend connections use approved secret references, not request-supplied credentials.

## Review focus

- Mutable adapter/request state could leak source scope between users; Tasks 1, 4, and 13 test concurrent identities with immutable read scopes.
- Hidden observations could contaminate node names, descriptions, embeddings, or paths; Tasks 11–13 test every derived field.
- An interrupted Neo4j/Qdrant write could publish mixed revisions; Task 10 injects each failure and tests attempt fencing and repair.
- Metadata edits or source replacement could leave filters stale or erase curation; Tasks 12 and 14 test live metadata, delta processing, and override persistence.
- A stale worker, delete, or suppressed node could resurrect content; Tasks 7, 10, and 14 test delayed writes, immediate visibility fences, and accepted-record immutability.

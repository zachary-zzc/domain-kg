# 独立双召回、合并候选、4B 过滤试验

2026-10-19。**已实现并实测；新题对照因连续两次超时提前停止，未完成验收，未构建完整 PDF。**

旧问题开发验证中，答案正确数从纯向量的 3/8 升到过滤方案的 5/8，引用完整均为
3/8。新题计划 24 道，只完成前五道的两组回答，均正确且引用完整；第六道过滤及
回退回答连续超时，按预设停止。不能将这五道前缀事实题报告成整批 100% 准确率，
也不能据此认定达到用户要求的 85% 答案 / 90% 引用完整率门槛。

## 本次实际测试的方法

1. 向量独立召回前六个片段；其中最多三个完整原文片段、1800 字符构成 V 基线。
2. 图独立以问题的前两个词汇匹配片段为种子，在原有名称/相邻片段图上遍历两步，
   最多检查 200 个节点、400 条边，取六个图候选。不使用向量排序作为图种子。
3. 合并去重，保留两条分支的排名。过滤输入首先保留 V 基线，再放入其他候选；按
   实际请求字节预算整段加入或省略，不截断原文，不由图结果预先覆盖向量候选。
4. 本地 Qwen3-4B 读取问题和候选原文，选择最多三个原文 ID。服务端检查范围、
   重复、数量及1800字符预算；空结果、非法结果或调用失败时回退向量基线。
   这些检查只保证结构有效，不能证明选择在语义上正确。
5. 仍由同一个 4B 使用原有回答提示词生成答案/引用。没有自动补引，没有把过滤器
   的解释、图摘要、参考答案或抽取事实注入回答上下文。

这次图仍为原文检索提示图，不是已经验证过事实关系的完整 KG；图边不能证明
实际使用、否定关系或因果关系。流程代码为 `eval/fusion_pilot.py`、
`eval/fusion_run.py`，测试前方案为
[冻结计划](superpowers/plans/2026-10-19-dual-retrieve-filter.md)。生产服务没有改动，
`fast` 模式也没有加入生成式过滤。这不是平台集成验收或完整图/过滤器消融。

## 开发验证：八道旧问题

选取上轮 p15、三道两段证据题和四道三段证据题。它们已被观察和讨论，所有结果
只能当开发验证。旧 V 基线的字节完全相同请求复用经哈希核对的原始响应；八次过滤
和八次新的过滤后回答均实际调用 4B，没有覆盖旧试验记录。

| 指标 | V 纯向量 | 双召回＋4B 过滤 |
| --- | ---: | ---: |
| 答案正确 | 3/8 | 5/8 |
| 引用完整 | 3/8 | 3/8 |
| 最终上下文找齐必要原文 | 4/8 | 4/8 |

完整候选证据覆盖为：V 前六 8/8，图六候选 6/8，合并及实际过滤输入均 8/8；
过滤后只剩 4/8。**在这些题上，证据已到手，过滤器仍丢掉了一半完整链条。**
必要证据本来就在 V 前六中，因此不能把开发阶段答案改善归功于图。

- p15：过滤器选择 h14，保留“24 小时内运动”的确切原文，修复了旧图路径挤掉
  证据的问题。回答及引用正确。
- Rho、Dales 两段题：过滤器选出两条必要来源，回答及引用完整。
- Cobalt 两段题：选对两段并答对，但只引 j06，漏引连接 Harbor 与 Northgate
  的 j05。候选过滤不能自动解决引用完整性。
- Orion 三段题：只选 j04，把明确未使用的 collector 分支当成实际分支，回答
  “Vault Flint”，应为 Mica。
- Harbor 三段题：丢掉项目/服务地点的起点，回答了错误地点的 petrol，应为 biodiesel。
- osprey 三段题：丢掉实际使用 helix-6 的起点，回答错误分支的 ridge，应为 marsh。
- Linden 三段题：答案 Vale Fen 正确，但过滤器丢掉起点 j09，引用链仍不完整。

三个错误分支的答案呈现为明确答案，而纯向量在对应题上拒答。答案正确数增加的
同时，错误表达形式也发生变化；不能只看 3 到 5 的变化就宣布方案可靠。

## 成本、资源与限制

开发阶段16次新请求全部完成，累计396.624秒；阶段含启动关闭406.942秒。
新题阶段16次请求，14次完成、2次超时，累计1066.737秒；阶段1084.663秒。
合计32次新请求、1463.361请求秒，已知输入11184 token、输出723 token；
两次超时调用的 token 用量未知，不能按零估计。

新题前五次成功过滤各用69.369–91.214秒，平均83.264秒。额外读取整批候选的
4B 推理成本明显，当前 CPU 运行条件下没有表现出适合作为低延迟过滤的证据。
这次测的是4B生成式过滤，尚不能评价其他过滤/重排实现。

保持 CPU 两线程、GPU0、单槽位、chat/embedding不同时驻留。chat两阶段采样RSS
峰值分别2,718,990,336和3,087,974,400字节，均低于3.5GB看门狗上限，监控未失败。
embedding峰值839,712,768字节，低于1.25GB。自有模型进程均已关闭；Python评测
因停止条件以非零退出，并不代表24题评测完成。

新题向量复用19个文本完全一致的原文向量，另外22个新片段、24道新问题真实生成
embedding；仍为1024维、完整输入覆盖、最多24实际token窗口加权池化。这不是
标准长窗口或最佳query指令配置的强向量基线。

停止后的只读主机快照显示负载约10.25、16GB物理内存中约15GB使用、压缩器约
7.7GB；`memory_pressure -Q` 给出33%系统可用比例。运行日志显示后段提示词处理
变慢。快照不能证明超时的唯一原因；没有确认OOM，也没有更改其他进程或系统配置。

428项unit/protocol检查通过（11.77秒），全仓Ruff、生产严格mypy（239模块）通过。
单独验证96次累计调用上限和连续两次超时停止。作者完成语义复核与代码自审，
无独立审阅者；本轮未改生产源码/配置/镜像，没有真实存储写入或发布。
